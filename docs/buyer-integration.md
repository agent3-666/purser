# Unpaid buyer preflight

`fetchUnpaidQuote` performs only the initial HTTP request. It refuses redirects, non-402 responses, absent x402 v2 `PAYMENT-REQUIRED` headers, a mismatched `resource.url`, and any caller-supplied payment or credential header. Only public `accept`, `content-type`, and `user-agent` request headers may be persisted. Use a pre-agreed GET or harmless POST body. This is a Purser policy for binding a quote to the requested resource; a rejected mismatch alone does not establish that the seller violates x402.

`verifyObservedQuote` calls the payee verifier for each parsed offer, independently fetching `https://<seller domain>/.well-known/x402-payee.json`. Use a persistent `PayeeLedger` when moving beyond a probe so rotation and nonce history survive restarts. A missing seller authorization is `unconfirmed`, never `confirmed`. Re-check immediately before any payment; the observed quote is time-sensitive.

The current `src/purchasing` experiment accepts only `local_native_transfer` offers. A real x402 HTTP offer must be marked `paymentRoute: "x402_http"`, which produces `payment_route_unsupported` in that executor. Sending a native transfer to the quoted `payTo` does not buy the resource.

`src/x402/gateway-buyer.ts` is a separate, opt-in single-attempt adapter for a pre-approved Arc testnet Gateway order. It re-parses the exact approved 402 header, fetches a fresh matching 402 before signing, binds the HTTP method, URL, body and public headers to the order, and requires a **confirmed** seller-domain payee authorization at the real current time by default. An `unconfirmed` payee may pass only with a separately supplied human exception that matches the exact order ID, request and quote digests, seller host, address, atomic amount and verifier reason codes, and expires within ten minutes. That is an explicit risk acceptance, not a new confirmation; `rejected` can never be overridden. Code cannot authenticate who created the exception object, so the operator must keep the approval record and signing path under their control. The adapter checks chain/USDC/Gateway contract and order/daily/lifetime caps, then writes an ignored 0600 local journal before signing. It requires a persistent payee ledger and records a confirmed seller's authorization before signing. A later order with the same request hash is rejected. Circle's `BatchEvmScheme` creates the EIP-712 Gateway authorization; the adapter sends the matching x402 v2 `Payment-Signature` exactly once, without deposit, redirect or automatic re-sign/retry. The Circle SDK gives this authorization an approximately seven-day validity window; unknown outcomes remain reserved and need manual reconciliation. The EIP-712 signature itself binds transfer fields, **not the HTTP request body**; the journal only constrains this buyer's sends and cannot guarantee that a seller will not reuse the authorization during its validity window. Keep the journal on private storage. Its rename-based writes cover process crashes, not a guaranteed power-loss recovery contract.

A successful HTTP response with a `PAYMENT-RESPONSE` is recorded as `server_ack_unverified`, **not independent Arc settlement**. The local experiment checks Circle's server-side batching discriminator and cryptographically recovers the EIP-712 signer from the received wire payload. It does not call Circle's live facilitator, prove deposited Gateway balance, or observe an Arc transaction. The official server SDK's `BatchFacilitatorClient.verify/settle` calls Circle's Gateway service; that real verification remains a live integration gate. Do not use this adapter on production funds. No testnet payment has occurred.

Run `npm run preflight:gateway -- <public-Arc-wallet-address>` for a read-only live check. It never loads the wallet key or signs. The 2026-09-29 19:02 UTC check of the Agent3 wallet found 5 ERC-20 testnet USDC, zero allowance to Gateway, and zero Gateway unified balance. The new QuickNode 402 offered 100 atomic testnet USDC units, but the seller-domain payee verdict was still `unconfirmed`; the buyer adapter refuses to sign by default. A separately reviewed per-order exception could permit this specific risk, but has not been approved or used. A Gateway deposit needs a token `approve` followed by the Gateway Wallet contract's `deposit`, and Circle's balance API must show the funded balance before a paid attempt. A plain token transfer to the Gateway contract is not a deposit. See [Circle's deposit guide](https://developers.circle.com/gateway/howtos/create-unified-usdc-balance) and [QuickNode's nanopayment documentation](https://www.quicknode.com/docs/build-with-ai/x402-payments).

For review, run `npx tsx research/probe_live_2026-09-29.ts` from the repository root. It captures the exact public 402 headers and body text in `research/live_quotes_2026-09-29.json` without payment. Do not interpret a 402 challenge as delivered value or external adoption. The prospective acceptance rules for the two internal tasks are in `eval/criteria.v1.json`; both remain blocked on unconfirmed payee authorization and live Gateway settlement, and GuardAgent also fails the current strict URL-binding policy.
